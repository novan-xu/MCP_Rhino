# MCP_Rhino Plan Log Rules

## 目标

本规则用于约束 MCP_Rhino 项目每一次能力演进的计划、执行、测试产物沉淀方式，保证"规划 → 执行 → 测试"三份产物结构一致、可追溯、可复核。

## 能力规划文档沉淀规则

- 在项目根目录维护 `Project_PLAN/` 目录，用于存放每次成功新增能力之前的计划总结文档。
- 当用户要求规划某个新能力，并且该能力随后 Execute 实现前，必须先补写一份对应的 Markdown 文档到 `Project_PLAN/`，再进行实际操作。
- 文档文件名必须使用英文，并遵循格式：`YYMMDD_PLAN_capability-name.md`。
- 文件名使用全小写英文（前缀 `PLAN` 除外），单词之间使用连字符 `-`，避免使用中文、空格或不稳定字符。
- 文件名应尽量简短、精炼，避免过长。
- 同一能力的 Plan / EXET / TEST 产物共享相同的 `YYMMDD_capability-name` 主体，仅前缀（`PLAN` / `EXET` / `TEST`）不同，保证三者一眼可对齐。
- 每份文档至少应包含：
  - **背景**：为什么要做，相关问题或用户诉求。
  - **目标**：本次要达成的具体能力或行为变化。
  - **架构归属**：按 `MCP_Rhino Architecture.md` 的目录归属规则，明确新增 / 修改组件落在哪一层（Tools / Skills / Agents / Application / Domain / Infrastructure / Contracts / Prompts）。
  - **关键设计**：接口签名、调用链、执行模式（Online / Offline）选择、Undo 策略、主线程封送等关键决策。
  - **涉及文件**：新增、修改、删除的文件清单（允许使用通配或目录汇总）。
  - **使用方式**：CLI / MCP Client / Plugin 侧的调用样例或交互说明。
  - **验收标准**：能力达成的可验证判据（返回码、副作用、Undo 行为、日志输出等），用于指导 EXET 阶段的测试记录。
  - **风险与回退方案**：已识别的风险点（兼容性、性能、线程模型、Rhino 版本差异等），以及若执行失败时的回退路径。
  - **后续扩展方向**：当前不落地但值得留档的扩展点，供后续 Plan 引用。
- Plan 定稿后若在 Execute 阶段发现偏差，原则上**不回写** Plan 文档，而是在对应的 EXET 文档「与计划的偏差」章节中记录；仅当偏差大到需要重新评审时才更新 Plan，并在文末追加 `## 修订记录（YYYY-MM-DD）` 节。
- 该文档沉淀步骤视为"能力完成"的一部分，不应省略。

## 执行文档沉淀规则

- 在项目根目录维护 `Project_EXET/` 目录，用于存放每次能力落地后的执行总结文档。
- 每一次依据 `Project_PLAN/` 中计划文档进行的 Execute 流程，在代码与测试通过之后，必须补写一份对应的 Markdown 文档到 `Project_EXET/`，才视为该能力收尾完成。
- 执行文档与计划文档一一对应：同一能力的 Plan 与 EXET 文件名共享相同的 `YYMMDD_capability-name` 主体，仅前缀不同。
- 文档文件名必须使用英文，并遵循格式：`YYMMDD_EXET_capability-name.md`。
- 文件名使用全小写英文（前缀 `EXET` 除外），单词之间使用连字符 `-`，避免使用中文、空格或不稳定字符。
- 文件名应尽量简短、精炼，避免过长。
- 每份文档至少应包含以下章节：
  - **对应计划**：链接到 `Project_PLAN/` 中的计划文档路径，并注明执行日期。
  - **关联产物**：指向本次执行对应的测试文件夹路径（`Project_TEST/YYMMDD_TEST_capability-name/`），以及相关 commit hash / PR 链接（若有），便于回溯。
  - **执行结果 / 实际落地范围**：按计划条目逐项确认落地情况，列出新增或改动的 Domain / Contracts / Application / Infrastructure / Skills / Tools 等组件。
  - **与计划的偏差**：本次执行中相对计划产生的删改、重命名、延后或放弃的条目，并说明原因；若无偏差也需显式声明。
  - **施工中发现并修复的问题**：执行期间暴露的实现缺陷、环境问题或测试盲点，以及相应修复动作。
  - **测试记录**：构建命令、smoke test / 集成测试命令、关键断言输出、使用的测试文件与工作副本路径、最终对象数等可复核信息。
  - **验收判据对齐**：对计划中「验收标准」逐项给出 PASS / FAIL / N/A 与证据（日志片段、返回值、Undo 栈截图等）。
  - **回退验证**：如计划中声明了回退路径，需在本节确认回退可行（至少做过一次手动 / smoke 回退演练）；不适用则显式声明 N/A。
  - **当前遗留项**：尚未覆盖的测试、未触达的路径、需要真实 Rhino / MCP Client 联调的部分，以及暂不处理的已知 issue。
  - **结论**：本轮执行是否达到可继续进入下一阶段（回归、联调、发版）的状态。
- 允许同一份 EXET 文档追加多轮复检结果（例如 `## 附加功能检查与修补（YYYY-MM-DD，第 N 轮）` 或 `## Post-Review (YYYY-MM-DD)`）。每一轮复检的发现、修补与测试结果都应原地追加，而不是新开文件；日期统一转为绝对日期。
- 执行文档中的路径、命令、退出码、对象数等核查信息应与仓库真实运行结果一致；禁止填写臆测值或占位符。
- 该文档沉淀步骤视为"能力完成"的一部分，不应省略；未沉淀 EXET 文档的 Execute 不视为闭环。

## 测试文件夹生成规则

- 在项目根目录维护 `Project_TEST/` 目录，用于存放每次能力落地所需的测试代码、测试数据、smoke 脚本等运行产物。
- 在实施 PLAN 过程中需要新增运行所需文件来验证添加的功能是否可行时，把相关文件添加到对应的 test 子文件夹中，而不是散落在仓库其他位置。
- 测试文件夹与 Plan / EXET 文档一一对应：同一能力的 PLAN、EXET 文件名与 TEST 文件夹共享相同的 `YYMMDD_capability-name` 主体，仅前缀不同。
- 文件夹命名格式：`YYMMDD_TEST_capability-name/`。
- 文件名使用全小写英文（前缀 `TEST` 除外），单词之间使用连字符 `-`，避免使用中文、空格或不稳定字符。
- 文件夹名应尽量简短、精炼，避免过长。
- 文件夹内建议包含（按实际需要裁剪）：
  - **测试代码**：`*.cs` 集成 / smoke 测试源文件，或独立脚本。
  - **测试数据**：`.3dm` 工作副本、JSON 请求样例、参考输出等；大文件应考虑是否纳入 git（必要时用 LFS 或在文件夹 `README.md` 中说明获取方式）。
  - **README.md（可选）**：说明该测试文件夹的运行命令、预期输出、依赖的 Rhino / MCP 环境。
- 测试文件夹需在对应 EXET 文档的「关联产物」与「测试记录」章节被显式引用，形成 PLAN → TEST → EXET 的闭环。
- 测试产物默认保留在仓库中，用于回归复查；若确认某份测试已被正式集成测试覆盖且不再需要独立留档，可在 EXET 文档中标注后整体删除该测试文件夹，禁止只删文件不更新文档。
